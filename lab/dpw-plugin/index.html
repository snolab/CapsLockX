#DPW# as a cross-platform plugin

The AHK side types a password when you type #DPW#. Porting it is two questions wearing one coat: generating a password is trivial and safe, retrieving a stored one is neither. This page separates them, and reports one concrete leak in the current effect executor that has to be fixed before the second one is built.

1 · What #DPW# actually does

It is a generator, not a vault

#DPW# does not type your password. It invents a fresh random one and types it. Nothing in this repository stores a secret — a repo-wide search for keychain / credential / vault / 1Password / Bitwarden finds only API-key plumbing in lib/otoji and nothing in the hotkey engine. That reframes the whole port: the feature that exists is cheap and safe, and the feature people assume exists is the expensive one.

It lives in one file, Modules/QuickInput.ahk — a grab-bag of "type a timestamp or a random string" hotstrings. The trigger:

:*?:#DPW#::  ; two-section random password
doubleSectionPassword()
return
Modules/QuickInput.ahk:117-119

That is an AutoHotkey hotstring, not a hotkey. :*?: is two options: * fires without waiting for an ending character (no space or Tab needed), and ? fires even inside a word. So the five characters #DPW# expand the instant the final # lands, anywhere, in any field. AHK's default behaviour also backspaces the trigger away before typing the replacement.

The body assembles two sections from a lookalike-free alphabet and types them joined by an underscore:

doubleSectionPassword()
{
    CharsFirst:="123456789ABCDEFGHJKLMNPQRSTUVWXYZ"
    CharsRest:="123456789abcdefghijkmnopqrstuvwxyz"
    section1 := GenPassword(CharsFirst, 1) GenPassword(CharsRest, 6)
    section2 := GenPassword(CharsRest, 7)
    QuickTextInput(section1 "_" section2)
}
Modules/QuickInput.ahk:78-85

Shape: Xxxxxxx_yyyyyyy — one uppercase-or-digit, then six lowercase-or-digit, an underscore, then seven more. 0, O, I and l are excluded on purpose, so it survives being read aloud or off a screen.

The generator and the typist are each three lines:

GenPassword(Chars, Length := 16)
{
    Min := 1
    Max := StrLen(chars)
    pw := ""
    Loop %Length% {
        Random StartPos, Min, Max          ; <-- Mersenne Twister, clock-seeded
        pw := pw SubStr(Chars, StartPos, 1)
    }
    Return pw
}

QuickTextInput(str)
{
    SendInput {Text}%str%                  ; <-- synthetic keystrokes
}
Modules/QuickInput.ahk:15-25 (GenPassword), 64-67 (QuickTextInput)

SendInput {Text} is the direct ancestor of clx's type_text: it injects the characters rather than pressing keys, so keyboard layout, Shift and Caps Lock do not enter into it.

Nine siblings share the same two functions — #PW#, #WPW# (identical to it), #NPW#, #HEX#, #HEXL#, #QPW#, #SPW#, #JPW#, #UUID#, plus the date/time ones (Modules/QuickInput.ahk:89-143). Any port should treat #DPW# as one profile of one feature, not as a special case.

2 · Where the AHK version is weak

WeaknessWhy it matters
Not a CSPRNG
QuickInput.ahk:21		 AHK v1's Random is a Mersenne Twister auto-seeded from the system clock. The nominal strength is ≈71 bits for #DPW# (14 chars over a 33/34-symbol alphabet) and ≈94 for #PW#, but a clock-derived seed is a far smaller space than that, and the generator is not designed to resist state recovery from earlier outputs. Every password from one script session comes from one seed.
The trigger is typed, then erased #DPW# is real keystrokes that reach the focused app before AHK backspaces them. In anything with incremental search, live collaboration or a "user is typing" channel, the literal string #DPW# — and the five backspaces — leave the machine.
? and * mean it fires anywhere QuickInput.ahk:117 Including mid-word, in a code editor, in a chat message, or in a field where the literal text #DPW# was what you meant. There is no confirmation step and no undo — the generated value replaces your text.
Write-only output The password is typed into exactly one field and never shown, stored or copied. A sign-up form with a "confirm password" box cannot be filled, and if the form is rejected the value is gone. In practice this pushes people toward the clipboard, which is worse.
Windows-only by construction AHK v1, SendInput, FormatTime. Nothing here ports; only the idea does.
#SPW#'s alphabet is buggy QuickInput.ahk:138 The symbol set contains ", " — a comma and a literal space. A generated password can therefore begin or end with a space, which many fields silently trim. Worth not reproducing.

3 · What clx offers today

The plugin contract is already exactly right for this, and it is one sentence: a plugin is any program that writes effects to stdout. clx plugin <command> [args…] spawns it and performs each line as it arrives (rs/core/src/plugin.rs:47-74). No SDK, no ABI, no manifest, and clx learns nothing about what the program is for. Typing is one verb:

k "text"        type a literal string  (\n \t \" \\ escapes)
k enter         tap a key
k c-c           a chord
w 200ms         wait
rs/core/src/effects.rs:8-20

So the entire "type a generated password" feature is a program that prints one line. That part is genuinely trivial. Three gaps are not:

GapDetail
No hotstring engine Nothing in rs/ matches hotstring, abbrev or any typed-character buffer. clx recognises gestures (trigger held + key), never typed text. There is no way to reproduce #DPW# as a trigger without building a rolling buffer of recent keystrokes inside the keyboard hook — a new and unattractive component to add to a process that also wants to type secrets.
clx plugin is Windows-only rs/core/src/plugin.rs is platform-agnostic and already used by rs/adapters/windows/src/main.rs:352-366. The macOS adapter's subcommand match (rs/adapters/macos/src/main.rs:52) has agent, dino, observe, ocr — and no plugin. That is a ~12-line addition, but it is a prerequisite for calling anything here cross-platform.
No binding from a key to a plugin clx plugin is a CLI subcommand only. The .clx binding layer that would let clx[ … ] call a plugin is a design, not code — there is no bindings loader in rs/core/src. Until it lands, invocation is a shell command or an OS-level shortcut.
Plugin stdin is null plugin.rs:51 Decisive for vault integration: a plugin cannot prompt on the terminal for a master password. It must rely on an already-unlocked session or on the vault's own GUI/biometric prompt.

4 · Does the current design leak a typed password?

A plugin's secret travels over its stdout pipe into clx. Pipes are not files, and clx does not write effect lines to any log on the success path. But three places print or retain them, and one is a real leak. This decides whether the retrieval feature is safe to build at all, so here it is explicitly.

Leak 1 — a malformed effect line is echoed in full, payload included

Any line the parser does not understand is printed verbatim to stderr:

Effect::Unknown(line) => {
    eprintln!("[CLX] unrecognised effect: {line}");
}
rs/core/src/effects.rs:431-434 (and :428-430 for Unsupported)

And k "…" is recognised only when the payload starts and ends with a quote (effects.rs:228-234). So a password containing an unescaped " produces a line that no longer ends in a quote → Unknown → the secret is printed to stderr. stderr is Stdio::inherit() (plugin.rs:52), so it lands wherever clx's own stderr goes — a terminal's scrollback, a watchdog log, a CI capture. This is a one-symbol quoting bug away at all times, and it fails silently.

Fix before shipping any retrieval plugin: never echo the payload. Print the verb and a reason, or redact everything between quotes.

Leak 2 — the revision buffer holds the secret in clx's heap

Runner.typed keeps a copy of the last typed string so retype can diff against it (effects.rs:340-363). This is already handled correctly by design: commit clears it, and plugin.rs:68 commits unconditionally when the plugin ends, however it ends. The residual issue is only that String::clear does not zero the freed bytes, so the plaintext can persist in the heap (and therefore in a crash dump or a swapped page) until reused. Worth knowing; not a reason to stop.

Non-leak — the hook's keystroke log does not record the characters, today

With CLX_DEBUG set, the Windows hook logs every key event to %TEMP%\capslockx_hook.log, and it logs injected events too — the is_ours early return happens after the log line (rs/adapters/windows/src/hook.rs:450-465). But what it prints is kb.vkCode:

debug_log(&format!("[hook] vk=0x{:02X} {:?} {} inj={} ours={} fg=[{}]", …));
rs/adapters/windows/src/hook.rs:451-459

Typed text is injected with KEYEVENTF_UNICODE (rs/adapters/windows/src/output.rs:122-137, 534-546), which reaches a low-level hook as VK_PACKET with the character in wScan — a field this format string does not touch. So the log records that a 15-character burst happened and exactly when, and which window had focus, but not what it said.

This is a fragile "no". It is one added field away from being a plaintext password log, and nothing in the file says so. A comment at that debug_log call, plus a test, is cheap insurance.

5 · Is typing a secret as keystrokes even sound?

Partly, and the two platforms fail differently.

Windows: every keyboard hook in every process sees it. That is not a hypothesis — it is how clx itself works. SendInput events are delivered to all WH_KEYBOARD_LL hooks, so any other tool the user runs (another macro program, an IME helper, a "productivity" utility, an actual keylogger) observes the injected password exactly as it observes typing. Injection is therefore no worse than typing it by hand, with two caveats: a human typing a password is at least aware they are doing it, and elevated windows reject injected input entirely (UIPI), so the feature quietly does nothing at a UAC prompt.

macOS: it will fail precisely where it matters most. When a real secure field has focus, the system enters secure input mode and disables event taps — clx already handles being switched off for this reason:

// When macOS disables our tap (e.g. during secure input / password fields),
// it sends a special event type. Re-enable the tap so it resumes working
// after the secure input ends.
rs/adapters/macos/src/hook.rs:240-244 — and engine.rs:276-279, emergency_stop

The same mechanism drops synthetic CGEventPost input into secure fields. So on macOS a password-typing plugin works in ordinary text fields and web forms and does not work at the login window, Keychain prompts, sudo, or any app using EnableSecureEventInput. That is a feature boundary to state up front rather than a bug to chase: this is for tokens and web forms, and a password manager's own browser integration is better wherever it reaches.

6 · Where the secrets would live — five options

Only relevant to the retrieval feature. The generator has no secret at rest and skips this table entirely.

Option Cross-platform Plaintext on disk? Secret in an argv? Setup burden
Generate, never store
what #DPW# does		 full OS CSPRNG everywhere never there is no secret no generated in-process none
Password-manager CLI
op · bw		 full both ship Win + macOS binaries never vault is encrypted; unlock is biometric no argv carries an item reference, not the value medium user must already use one; bw needs a session token in an env var — prefer op
pass
gpg + files		 partial native on macOS, awkward on Windows (gpg4win + shell) never gpg decrypts to stdout no high GPG key management, agent lifetime
age/gpg file managed by clx full single static binary never if decryption stays in memory risk a passphrase flag would be visible — must not exist high and stdin is null, so there is nowhere to type the passphrase
OS credential store
DPAPI · Keychain		 none shared two unrelated APIs, two implementations never encrypted at rest no medium but see below

Why the OS credential store scores badly despite encrypting at rest

DPAPI's whole design is that any process running as the user decrypts silently, with no prompt and no audit — so a vault in Credential Manager is protected against someone reading the disk and against nothing else. macOS Keychain is stronger (per-item ACLs, a prompt, Touch ID) but shares no code, no model and no CLI with it. Choosing this means writing and maintaining two half-vaults with different security properties, which is strictly worse than delegating to software whose entire job is that.

7 · Recommendation

Split the feature in two. Build the first now; delegate the second, and only after the stderr leak is fixed.

7.1 — clx-genpw: ship it

This is what #DPW# actually is. It has no secret at rest, no vault, no unlock, and no cross-platform story to invent: it is a program that reads the OS CSPRNG and prints one k "…" line. It inherits all of the security analysis above and none of the risk, because the value it types did not exist a millisecond earlier and is not a credential to anything yet. It fixes both real defects of the AHK version — the clock-seeded Mersenne Twister becomes a CSPRNG, and the typed-then-backspaced trigger disappears because clx uses gestures, not hotstrings.

7.2 — clx-pw: delegate to the user's password manager

For retrieval, clx should own none of it. The plugin shells out to op (or bw, or pass), reads the value from that process's stdout, escapes it, prints one k "…" line, and exits. Reasoning, in order of weight:

  1. clx never becomes a place secrets live. No new storage format, no key management, no unlock UI, no migration, no backup story — and no obligation to be as careful as a password manager, because it never holds the vault.
  2. Unlock is already solved, and stdin is null. op raises its own Windows Hello / Touch ID prompt out of band. Every design where clx handles the passphrase collides with plugin.rs:51.
  3. argv stays clean. clx plugin clx-pw "Example Login" puts an item name in the process table — visible to other processes as it always is, and harmless. The value never appears in an argument.
  4. Same command on both platforms. The only clx change needed is adding plugin to the macOS subcommand match.
  5. It degrades honestly. No op installed → the plugin prints nothing and exits non-zero → clx types nothing. A missing feature, not a wrong password in a field.

If the user has no password manager, the fallback is pass or an age-encrypted file invoked as an external command the same way — a different plugin, not a different clx.

8 · The concrete plugin design

What the plugin is

Two small programs, neither of which clx knows anything about. Each prints effects and exits. Written in whatever is convenient — Rust beside the other binaries, or PowerShell/shell on the model of scripts/clx-plugin-demo.ps1.

What it emits — generator

$ clx-genpw dpw
k "Xxxxxxx_yyyyyyy"

$ clx-genpw quad
k "AAAA-BBBB-CCCC-DDDD"
shapes only — every character above is a placeholder

One line, one effect, nothing else. Profiles mirror the AHK family (dpw, pw, quad, hex, num, uuid, iso-date …) so the nine hotstrings become nine arguments to one plugin rather than nine features. Rules: OS CSPRNG (getrandom), rejection sampling rather than % len so the alphabet stays uniform, the lookalike exclusions kept, and no leading or trailing space ever — that is #SPW#'s bug.

What it emits — retrieval

$ clx-pw "Example Login"
k "<value from op, with \" and \\ escaped>"

Nothing else — no banner on stdout, diagnostics on stderr only, and never the value on stderr. Escaping is the plugin's responsibility and is the one place a bug becomes a disclosure (see §4). A shape worth considering for two-field forms, since it costs nothing extra:

# username, Tab, password — the whole login in one gesture
k "<username>"
k tab
k "<value>"

How the user invokes it

# today — the contract as it exists
clx plugin clx-genpw dpw
clx plugin clx-pw "Example Login"

# once .clx bindings land (/lab/clx-lang/)
clx[ ; ] => clx-genpw dpw

What it should not be is a hotstring. Reproducing #DPW# literally means giving clx a rolling buffer of recently typed characters inside the keyboard hook — new machinery, in the hottest code path in the program, whose entire purpose is to remember what the user typed. For a password feature that trade is bad in both directions. A gesture is also strictly better behaved: nothing is typed and erased, and it cannot fire by accident inside a word.

Prerequisites, smallest first

  1. Redact the payload in effects.rs:428-434. Blocks the retrieval plugin; good hygiene regardless. (~5 lines + a test.)
  2. Add plugin to the macOS subcommand match (rs/adapters/macos/src/main.rs:52). Blocks "cross-platform". (~12 lines.)
  3. Comment the VK_PACKET property at hook.rs:451 so nobody adds wScan to that format string later.
  4. Then clx-genpw. Then, separately, clx-pw.

9 · What I would not do

  • Not store passwords in clx. Not in config_store, not in ./tmp/, not in a clx-managed encrypted file. The moment clx holds a vault it inherits an obligation it is not built for.
  • Not add a secret-aware verb (pw, secret, type_secret) to the effect language. Effects, not domains is the whole reason this contract works; a verb that means "this one is sensitive" hands clx a category it then has to reason about. The redaction in §4 should apply to every payload, which is simpler and strictly safer.
  • Not pass a secret as a command-line argument, ever — not to clx plugin, not to a helper. The process table is readable by other processes running as the same user.
  • Not route it through the clipboard. The effect language has no clipboard verb and should not gain one for this: on Windows, Clipboard History and cloud sync would archive the password, and opting out requires setting the clipboard-exclusion formats correctly — work a password manager has already done and clx would get wrong.
  • Not build a DPAPI/Keychain mini-vault — two implementations, two security models, and DPAPI offers no protection against the threat that matters (other code running as the user).
  • Not reproduce the hotstring trigger for the retrieval half under any circumstances, and preferably not for the generator either (§8).
  • Not run either plugin with CLX_DEBUG set until §4's fix is in, and say so in the plugin's own --help.

10 · What needs a decision

Q1 — Is retrieval wanted at all? needs a decision

The existing feature is a generator. If the generator is all that was meant, this is a half-day of work with no security surface and §7.2 can be dropped entirely. Everything expensive on this page exists only if you want clx to type a stored password.

Q2 — Which vault CLI? needs a decision

op is the best fit (biometric unlock out of band, clean cross-platform binaries, no session token to park in an env var). bw works but wants BW_SESSION in the environment, which is readable by other processes running as you. pass is fine on macOS and painful on Windows. Which do you actually use?

Q3 — What gesture? needs a decision

Under a held trigger, the letters are nearly all taken (HJKL YUIO G T N P WASD V B M Z X C, digits 1-9). A generator wants one binding plus a way to pick a profile. Options: one key cycling profiles, a two-key sequence, or the punctuation keys. This only matters once .clx bindings exist; until then the shell command is the interface.

Research only — nothing here is implemented, by request. The one finding that is independent of any decision above: rs/core/src/effects.rs:428-434 echoes an unparsed effect line verbatim to inherited stderr, so a quoting bug in any plugin discloses its payload. Worth fixing whether or not this feature is built.
