CapsLock+Space[number row] — F1–F12

Using the two-trigger chord as the layer selector instead of Alt. Full edge-case audit and blast radius. Nothing implemented yet.

CapsLockX 2.0 · branch beta Rust core + Windows adapter 2026-09-04

The idea is better than the Alt variant — three whole problem classes vanish

1. Alt+Space keeps its Windows window-menu behaviour; the Space bypass rule is untouched. 2. No Alt suppression, so no Alt+F4 hazard, no menu-bar activation, no AltGr problem, no GetAsyncKeyState unknown. 3. CLX[1–0] (virtual desktop) and CLX+Shift[1–0] (move window) are preserved exactly, because a two-trigger chord is a genuinely different gesture rather than a modifier the desktop module was ignoring.

And your intuition about modifiers is right: Ctrl/Shift/Alt/Win stay physically held and decorate the injected F-key for free. Alt+CapsLock+Space[4] is a real Alt+F4 — now a feature rather than an accident.

But the chord is already taken — and it locks eagerly

You're right that CapsLock+Space is the CLX-lock gesture, and the collision is worse than a naming clash: clx_dn calls enter_clx_mode() the instant the second trigger goes down, before any digit is pressed. So CapsLock+Space[1] would emit F1 and leave you in locked CLX mode — your next hello becomes cursor-left, page-nav, and friends. Every single use of the F-layer would strand you in locked mode.

The fix is a one-word change in discipline: make the lock deferred — decided on release, and skipped when the chord was consumed by another key. That is exactly the fn_acted tap-vs-hold rule CLX already applies to a single trigger.

Notation

A gesture is a timeline, not a set of keys — and every bug in this document lives on a press or release edge. So the notation makes those edges explicit: (…) groups keys, [ is the moment the group goes down, ] is the moment it comes back up, and a bare key name in between is a tap.

TokenReads asRule
( a+b )groupKeys treated as one unit. + is commutative (交换律) — press order within a group is irrelevant. Parentheses are optional for a single key.
[… goes downThe group to the left is pressed and held. Everything after it happens while it stays down.
]… comes back upThe hold ends. All keys in the group must be released — letting go of just one does not close the bracket. This is the rule the deferred lock toggle turns on.
ktapA bare key name is struck and released. Several in a row are taps in sequence.
X.tap the groupDown and straight back up with nothing in between — sugar for an empty body, X[ ]. space. is a literal space character; (s+c). is the lock toggle.
( a|b )either oneAlternation, and commutative like + — but it means one of these, not both of these. (space|capslock) is "whichever trigger you happen to use".
clxabbreviationShort for (space|capslock). clx[ h ] is the familiar "hold a trigger, tap H".
nestingexplicit orderOrder is only expressed where it matters: an inner hold was pressed after the outer one, and is released before it.
X[ unclosednever releasedA hold with no ] is a key that was never let go — the shape of the stuck-modifier bug in M5 / B8.

Why the brackets earn their keep here

The whole proposal turns on release semantics: the lock toggle must fire on the release of the last trigger, a partial release must not count, and the release order of the two triggers decides whether a stray character escapes (T4). A flat "hold-plus-key" notation cannot say any of that. This one says it in punctuation.

The three modes, written down

Your question — whether a locked session behaves exactly like a held trigger — has a precise answer in the code, and the notation turns out to say it neatly. on_key_event step 4 gates on is_clx_active(), which is true for both CM_FN and CM_CLX, so a non-trigger key is dispatched through the identical path either way.

NotationModeWhat it means
hCM_NORMALA key is just a key.
Space|CapsLock[h]CM_FNA trigger is physically held. The hold span is bounded by your finger.
Space+CapsLock.  then  Space|CapsLock[ CM_CLXYes — locked mode is the same hold span, just unclosed. The chord tap opens a hold that outlives your fingers; every later key lands in the same dispatch path as CM_FN. The lock is not a separate behaviour, it is a bracket nobody closed.

Two caveats before you rely on that equivalence

You cannot nest a hold inside the lock. Pressing a trigger while locked runs enter_fn_mode(), which does mode &= !CM_CLX — the outer bracket is torn up by the inner press rather than nesting inside it. So clx[ … clx[ … ] … ] is unwritable, by construction.

That is also the mechanism behind L4. Because the lock bit is already gone by the time clx_up tests is_clx_locked(), the "unlock instead of emitting" branch never runs and a real CapsLock is tapped instead. In notation: the ] you meant to write silently became capslock. — an actual keystroke leaking into your document, and your Caps Lock LED with it.

One more consequence worth stating plainly: in locked mode space. both types a space and closes the lock, because Space is a trigger and is consumed by step 3 before the module dispatch of step 4 ever sees it.

When does each part fire?

The bracket is not a trigger condition. A key in the body acts on its own key-down, the moment it is struck — modules.on_key_down is called from step 4 of on_key_event, long before anything is released. Only the closing bracket waits.

WrittenFires onConsequence
(s+c)[ 1the 1 key-downF1 is already emitted. The ] is not needed to make the combo work — you may leave it off when the point is that the action has happened regardless of how the hold ends.
…]release of the last key in the groupDecides only what the chord meant: empty body → toggle the lock, non-empty body → the body already did the work, so do nothing.

This is why the deferred lock needs no timeout

Because every key in the body has already fired by the time ] arrives, "was the body empty?" is answered by then — no hold threshold, no timer, no guessing at intent. That is the one property that makes L1 implementable as a clean rule rather than a heuristic, and it is exactly where the existing 200 ms Space timeout (T2) went wrong by guessing on a clock instead.

Typed plainly: (s+c). taps the chord, (s+c)[ 1 ] is the proposed F1, (s|c)[ h ] is any ordinary CLX binding, capslock[ alt[ space[ 1 ] ] ] is the T1 failure, and clx[ on its own is locked mode. All ASCII — this has to survive being typed into CLAUDE.md, a commit message, a Rust doc comment and the HUD.

1What the chord does today

Traced through rs/core/src/engine.rs and rs/core/src/state.rs. Two surprises are hiding in here.

// engine.rs :: clx_dn — chord is detected from prior_key, and locks immediately
let chord = (code == CapsLock && prior == Space) || (code == Space && prior == CapsLock);
if chord {
    self.state.enter_clx_mode();          // <- LOCKS on key-DOWN, before any digit
    self.store_trigger(code);
    self.fn_acted.store(true, ...);       // <- so release never re-evaluates
    return false;
}

// state.rs :: the mode bits
enter_fn_mode()  { mode |= CM_FN;  mode &= !CM_CLX; }   // <- pressing a trigger CLEARS the lock
enter_clx_mode() { mode |= CM_CLX; }                    // <- always sets; never toggles

Surprise 1 — the chord is not a toggle

enter_clx_mode() is fetch_or: pressing the chord while already locked just locks again. What actually unlocks is a single trigger tap. So the gesture is asymmetric: chord to lock, tap to unlock.

Surprise 2 — the unlock branch is dead code

clx_up tests is_clx_locked() to decide "unlock instead of emitting the native key" — but enter_fn_mode() already cleared CM_CLX on the key-down. The test is always false, so the else branch runs and taps a real CapsLock. See L4.

11Recommended solution

The one behavioural rule that makes it work

A chord that did something is not a lock request. CapsLock+Space. toggles the CLX lock only when it is released without any other key having been pressed — the same tap-vs-hold discipline fn_acted already applies to a single trigger. Everything else follows from that.

Shape of the gesture logic

// engine.rs :: clx_dn — chord from held_keys, and NO eager lock
let other = if code == CapsLock { Space } else { CapsLock };
let chord = matches!(code, CapsLock | Space) && self.held_keys.lock().unwrap().contains(&other);
if chord {
    self.state.set_chord_active(true);
    self.state.set_chord_was_locked(self.state.is_clx_locked());  // L6
    self.state.enter_fn_mode();       // active, but NOT latched
    self.store_trigger(code);
    self.fn_acted.store(true, ...);   // suppresses the native Space/CapsLock tap
    return false;                     // never bypass -> Alt+Space rule untouched
}

// engine.rs :: clx_up — decide the lock on release of the LAST trigger
if self.state.chord_active() && !self.other_trigger_still_held(code) {
    if self.state.chord_acted() {
        self.state.restore_pre_chord_lock();   // chord was consumed -> no toggle
    } else {
        self.toggle_clx_lock();                // clean chord tap -> real toggle
    }
    self.state.set_chord_active(false);
}
