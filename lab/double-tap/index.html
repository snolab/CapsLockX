Double-tap: worth having?

The one common keyboard gesture the CLX notation cannot write. Whether that is a gap or a feature.

Decision (2026-09-14): no double-tap feature

Not a gesture in the notation, not an operator in .clx, no new engine or platform plumbing (no double_tap_ms(), no repeat-rate readout). The research below stays as the reasoning; the conclusion was that the one good form is already the only one in use — the voice module's look-back on V — and it is left exactly as it is, hardcoded 500 ms included. Revisit only if a second module genuinely needs tap-vs-double.

Short answer

Yes in one specific form, no as a general primitive. There are two ways to build a double-tap, and they are not the same gesture. Look-back — the single tap fires at once, and a second tap inside the window upgrades it — costs nothing and needs no timer. Wait-ahead — the first tap is held back until the window expires to see if a second arrives — taxes every single tap with the full interval and reintroduces the timer-thread bug class this project just spent a week on. The voice module already does the right one. Keep that shape, source the interval from the OS instead of hardcoding it, and do not add double-tap to the pattern language.

2Two gestures wearing one name

Look-back — compare on the second tap

Tap 1 fires its action now. Tap 2 checks "was tap 1 within T?" and, if so, upgrades what tap 1 started.

Latency: zero. Timer thread: none — one Instant and a comparison. Failure mode when the window is missed: two ordinary taps.

Requires: the single-tap action must be something a second tap can build on — start a mode, begin a hold, open something. It cannot be a one-shot side effect you would need to take back.

Wait-ahead — decide after the window

Tap 1 is held back. A timer fires at T: if no second tap came, run the single action late; if one did, run the double action.

Latency: every single tap arrives T ms late, always. Timer thread: required — the same detached-thread-with-a-deadline shape as the 200 ms Space timeout that produced the space flood. Failure mode: the wrong action fires, after a delay, and there is no undo.

Requires: tolerating the latency. On navigation keys that is the whole product.

Nearly every complaint about double-tap in the wild is a complaint about wait-ahead: sluggish single-clicks, tap-dance keys that feel mushy, the IDE that eats your first Shift. Nearly every double-tap people like — iOS double-space to period, double-tap Shift to caps on a phone — is look-back, sometimes with a small retroactive edit (the first space is typed at once; the second replaces it with ". ").

4What it buys

  • Toggle/lock semantics that feel natural. "Tap to do it once, tap-tap to make it stick" is a widely understood idiom (double-tap Shift → caps lock on phones). The voice module's use is exactly this, and it is the strongest case for keeping double-tap at all.
  • Binding space without new keys. Real, but the chord layer already delivers a whole extra layer structurally, with no clock. Double-tap is the weaker tool for this job.
  • Familiarity. Users arrive knowing it from IDEs and phones.

The systems that feel good either use look-back or use no timer at all. The 500 ms already in voice_ptt.rs matches the desktop OS default, which is not a coincidence — it is what users have already calibrated their hands to.

7Recommendation

The rule

Look-back double-tap is allowed; wait-ahead is not. Concretely: the single tap must fire immediately, the second tap may only upgrade something the first tap started, and the implementation is a stored Instant compared on the second tap — never a thread that wakes up later to decide. That rule keeps zero latency, keeps the notation edge-based, and keeps the engine at exactly one timer (the Space hold-timeout), which is already one more than anyone wants.

  • Interval: take it from the OS, fall back to 500 ms. Add Platform::double_tap_ms() -> Option<u64> beside the existing system_key_repeat_ms(); Windows answers with GetDoubleClickTime(), macOS with NSEvent.doubleClickInterval. The user has already tuned that number for their hands, and accessibility settings flow through for free. Replace the hardcoded DOUBLE_TAP_MS in voice_ptt.rs with it.
  • One constant, not three. Retire 250 and 200 from the conversation; they belong to AHK code that is either superseded or unported.
  • Factor the voice pattern into a reusable helper — a TapUpgrade that a module can consult — so the next module that wants "tap = do, tap-tap = lock" reuses the safe shape instead of inventing a timer.
  • Do not add it as a general gesture. Every case where it seems attractive (a layer, a lock) has a structural equivalent that needs no clock: the chord.

The alternative worth a thought: make voice lock structural too

Voice lock is the only timing gesture left in the engine. It could be (capslock+space)[ v ] instead — chord + V — which is exactly how the F-row layer already works, needs no interval at all, and makes "lock" mean the same gesture family everywhere. The cost is ergonomic: a double-tap of V is one finger, the chord is two hands. The recommendation above keeps double-tap because it is the good kind; but if you would rather have zero timers, this is how.

8What it means for .clx

This settles open question Q4 on the language page. Top-level sequences like clx[ v ] clx[ v ] should not become a general double-tap operator — the language stays edge-based. If a binding needs tap-vs-double, it is a property of the action, not the pattern:

clx[ v ]   => voice hold          # single tap: hold-to-talk (fires at once)
clx[ v ]   => voice hold, x2 lock # second tap inside the OS double-tap window upgrades to locked

That keeps the pattern side honest (one gesture, one binding) and puts the timing where it belongs: inside a built-in that has explicitly opted into upgrade semantics, with the interval coming from the platform.
