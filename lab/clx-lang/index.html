Where the language is ahead of the engine

  
The Platform trait today has mouse_move(dx, dy) — relative only — plus mouse_button and scroll_v/h. There is no cursor-position getter, no absolute move, no window rect, no screen size, and no element lookup. Even the agent's m c (click where the pointer is) is unimplemented in clx-agent.rs ("will fix with proper tracking"). So of the target forms above, only cur offsets and marks run on the engine as it stands. The rest are honest requirements, not promises — and @"element" on Windows means a UI Automation client that doesn't exist yet.






  
Pointer keys on the pattern side

  
mb1–mb5 (aliases lbtn rbtn mbtn xbtn1 xbtn2), wheelup, wheeldown parse as keys, so mb4[ h ] or clx[ wheeldown ] are writable. They are flagged with a warning: the engine hooks the keyboard only (WH_KEYBOARD_LL; a CGEventTap with the keyboard mask on macOS). Seeing mouse buttons as triggers needs a second hook, and on Windows a WH_MOUSE_LL callback shares the same UI-thread hazards this project has already been bitten by.






  
A decision made while writing this: single letters are always letters

  
The first draft had s and c as aliases for the triggers, so (s+c) was short and pleasant. It also made clx[ c ] — tile windows — silently mean CapsLock. Aliases that shadow real keys are removed; clx, space and capslock stay.





Grammar (EBNF)


file      := { line NEWLINE } ;
line      := [ binding | scope ] [ comment ] ;
scope     := "when" predicate ( "{" { line NEWLINE } "}" | binding ) ;
predicate := matcher { "+" matcher } ;                 (* all must hold *)
matcher   := ( "app" | "class" | "title" ) ":" STRING ;
binding   := pattern "=>" action ;
pattern   := gesture { gesture } ;                     (* juxtaposition = sequence *)
gesture   := holdable ( "[" [ pattern ] [ "]" ] | "." | ε ) ;
holdable  := key | "(" key { ( "+" | "|" | "->" ) key } ")" ;
key       := IDENT | DIGIT | "-" | "=" ;               (* punctuation keys also by name: minus equal comma ... *)
action    := "{" [ command { ";" command } [ ";" ] ] "}" | command | script ;
script    := "js" "{" ... "}" ;                        (* opaque to the .clx parser *)
command   := pointer | IDENT { arg } ;
arg       := IDENT | NUMBER | DURATION | STRING | MODKEY ;
pointer   := ( "m" | "hover" ) target [ "c" ]
           | ( "click" | "dbl" ) [ button ] [ target ] [ "x" DIGITS ]
           | "drag" target "->" target [ button ]
           | ( "md" | "mu" ) [ button ]
           | "scroll" ( "up" | "down" | "left" | "right" ) [ DIGITS | PX ] [ target ]
           | "mark" IDENT ;
target    := coord coord | ( "win" | "cur" | "screen" ) coord coord | "cur"
           | "@" IDENT | "@" STRING | "@" IDENT ":" STRING ;
coord     := [ "+" | "-" ] ( DIGITS | PCT ) ;
button    := [ MODS ] ( "l" | "r" | "m" | "x1" | "x2" ) ;
MODKEY    := ( "c-" | "s-" | "w-" | "a-" )+ IDENT ;
DURATION  := DIGITS ( "ms" | "s" ) ;




  
The one design move that makes this cheap

  
The action half is not new. clx agent --exec already parses and executes k/m/w/wf/scan (parse_line in clx-agent.rs). A .clx binding's right-hand side is a line of that language, so the engine can hand it to code that already exists. Only the pattern half is genuinely new — and it is the notation the recognizer already speaks.





3 · when — app-scoped bindings


Every App-* module in the AHK tree is context-guarded, because an app binding is meaningless outside its app. App-OneNote.ahk alone carries five #if guards — #if OneNote搜索界面内(), #if OneNote笔记编辑窗口内(), and so on. The draft above has no equivalent, so no App-* module can be expressed in it at all. This is the missing construct.





ConstructExampleMeaning



scope blockwhen app:"ONENOTE.EXE" { … }Every binding inside is live only while that app owns the foreground window.


scope, single linewhen app:"ONENOTE.EXE" clx[ d ] => k "{date}"Same thing for one binding. No block needed.


matchersapp:"ONENOTE.EXE", class:"Framework::CFrame", title:"*OneNote*"Executable name (case-insensitive), window class (exact), title (glob). Matches AHK's ahk_exe / ahk_class / title triple.


conjunctionwhen app:"ONENOTE.EXE"+title:"*搜索*"+ means all must hold — the same connector the pattern half uses for "held together".


nestingwhen app:"X" { when title:"*Y*" { … } }Inner predicate is ANDed with the outer. This is how the five OneNote sub-contexts nest under one app.





Worked example — the shape a ported App-OneNote would take:


# bindings.clx
when app:"ONENOTE.EXE" {
  clx[ d ]  => k "{date}"              # 日期 — SNODateStringGenerate
  clx[ l ]  => js { await onenote.insertLink() }

  when title:"*搜索*" {                  # #if OneNote搜索界面内()
    clx[ g ] => k enter
  }
}




  
The predicate is evaluated inside the hook — so it can never be a script

  
Scope decides whether a binding exists, and that decides whether the key is suppressed — which WH_KEYBOARD_LL must answer synchronously, before returning. So a predicate has to be something the hook can evaluate in microseconds: foreground HWND, its class, its title, its executable. Nothing else. An arbitrary user predicate is not admissible here, for the same reason a script handler cannot decide suppression (§4).

  
Even those four are not free. hook.rs already gates its GetForegroundWindow + class lookup behind debug_enabled() precisely "so the lookup never runs on the hot path in production" — the repo has already priced this. The implementation therefore has to cache the resolved {exe, class, title} keyed on HWND and refresh it on foreground change (a WinEventHook on EVENT_SYSTEM_FOREGROUND, off the hook thread), not re-query per keystroke. If no scoped binding is loaded, the whole lookup is skipped.







Resolution ruleBehaviour



specificityA matching scoped binding shadows a global one for the same pattern. More matchers = more specific = wins.


tiesTwo equally specific scopes both matching the same pattern is a load-time diagnostic, not a silent last-one-wins.


fallthroughA pattern with no scoped match falls back to the global binding if one exists; otherwise the key is not ours and passes through.


cost when unusedA file with no when compiles to exactly the table it does today. Scoping is pay-for-what-you-use.





4 · Embedded scripting — the js escape hatch


The Lua model — Neovim, WezTerm, and above all Hammerspoon, which is essentially this project on macOS — is a declarative table for the common case plus a real language for everything else. .clx wants the same split. There is even direct precedent in this repo: Modules/CLX-NodeEval.ahk already lazily spawns a long-lived node server on port 29503, POSTs code to it, and reads the result back.




  
The dividing line is not "simple vs complex"

  
Three questions decide where a feature belongs, in order:

  
    
    
  1. Must the hook decide it synchronously? → Rust. No exceptions.
    2. 
    
  2. Does it need a platform capability Rust does not expose yet? → then a script does not help. JS can only compose what the Platform trait already hands out; the gaps listed in §2 (no cursor getter, no window rect, no element lookup on Windows) block a JS handler exactly as hard as they block m @"OK".
    3. 
    
  3. Core-for-everyone, or personal glue? → only now is the split real.
    4. 
  

  
So: Rust for the engine and anything the hook touches; JS for app glue — compositions of existing verbs, scoped to one application, that do not belong in everyone's binary. Composition and ownership, not complexity.





The two candidates that prompted this land on opposite sides, which is what makes them a useful test:





FeatureWhat it actually isBelongs in



CLX-WindowManager
1,111 lines		Mostly EnumWindows, monitor rectangles, Z-order and tiling arithmetic — raw Win32, almost no composition. cycle_windows is reached from hook dispatch. Expressing it in JS means exposing ~15 new platform APIs so that JS can reimplement, more slowly, something that already works.Rust (already is)

And it is personal: nobody else's binary should carry a OneNote ribbon driver.JS





Two-tier execution



  
A script handler can never decide suppression

  
WH_KEYBOARD_LL has a LowLevelHooksTimeout (~300 ms default): exceed it and Windows silently unhooks you, and the keyboard is simply gone. Every scar in this project is that bug class — COM refused inside the hook → the clx-vd-worker thread; WebView2 in the hook process killing the hook → out-of-process prefs; a panic across extern "system" → 0xC0000409. Running arbitrary user code there is the same bug again, with an unbounded body.

  
So the pattern half is matched in the hook against a precompiled table (microseconds, decides suppress/pass immediately), and a js { } handler is posted to a script worker and forgotten — exactly the shape of vd_api::post. The consequence is a language rule, and it is free to decide now and painful later: suppression is declared by the pattern, never returned by the script. The [ ] hold form already implies it.

TypeScript without a typechecker in the binary

  
No embeddable engine runs TS. The expensive answer is to type-strip at load with oxc_transform (pure Rust, very fast) or swc. The cheap answer gets most of the value: ship a clx.d.ts and let the user's editor do the typechecking, then run plain JS. Full autocomplete and red squiggles in VS Code, zero TS machinery shipped. Add stripping later if people actually write annotations.





API surface — clx.d.ts sketch


The boundary is the Platform trait plus the agent verbs, so the API is mostly a rename of things that already exist. Marked gap where §2's missing platform capabilities bite equally hard:


declare namespace clx {
  function key(spec: string): Promise<void>;        // "c-c", "a-f4", "f1"  — exists
  function type(text: string): Promise<void>;       // exists
  function wait(ms: number): Promise<void>;         // exists
  function waitFor(text: string, ms?: number): Promise<boolean>;  // exists (UIA on Windows: gap)

  const clipboard: {
    text():             Promise<string>;            // exists
    setText(s: string): Promise<void>;              // exists
    setHtml(s: string): Promise<void>;              // gap — App-OneNote needs it (WinClip)
  };

  const win: {
    active(): Promise<{ exe: string; cls: string; title: string;
                        x: number; y: number; w: number; h: number }>;  // rect: gap
    activate(m: WinMatch): Promise<boolean>;        // exists
    exists(m: WinMatch):   Promise<boolean>;        // exists
  };

  const mouse: {
    pos():  Promise<{ x: number; y: number }>;      // gap — no cursor getter
    move(x: number, y: number): Promise<void>;      // gap — relative only today
    click(button?: "l"|"r"|"m", n?: number): Promise<void>;          // exists
  };

  function notify(msg: string): void;               // tray balloon
  function log(...args: unknown[]): void;           // → tmp/clx-script.log
}





DecisionWhy



one long-lived context per fileNot a fresh eval per keystroke. Handlers closing over module state is precisely what makes Lua configs pleasant, and it makes startup cost a one-time ~1 ms.


catch_unwind at the boundaryA panic crossing the Rust↔JS edge aborts the process (0xC0000409 — the crash this repo already has a firewall for). JS exceptions are values in QuickJS, not panics, but the binding layer still needs the firewall, and a throwing handler must surface as a tray diagnostic, never a crash.


re-entrancy is already solvedA handler calling clx.key("a") injects input that comes straight back through the hook — CLX_EXTRA_INFO tagging already filters self-injected events. Nothing new to build.


scripts live beside the bindingsbindings.clx plus a sibling scripts/ directory; js { } bodies are inline, import-able modules are files. Hot-reloaded on save with the same keep-last-good-set rule as Q6.





5 · Compiler / AST tooling — what to use


The grammar above is about 14 token kinds and no left recursion. That constrains the answer more than any library's feature list does.





OptionWhere it runsAssessmentVerdict



Hand-written recursive descentJS and Rust~350 lines each, spans on every node, error recovery per line, zero dependencies. This page runs one. Ports to Rust line-for-line, and the Windows build — which has already proven allergic to heavy crates — gains nothing new to compile.recommended

What actually keeps two implementations honest: a conformance corpus, not a shared grammar

  
Whatever parses .clx in the lab and whatever parses it in the engine must agree. A shared grammar file feels like the guarantee but isn't — the semantic layer (aliases, duplicate detection, edge IR) lives outside the grammar. A directory of .clx inputs with expected {bindings, edges, diagnostics} JSON that both implementations must pass is the guarantee, and it doubles as the language's spec-by-example. The JS side already proved this works: parse.test.cjs caught two real bugs a visual check had missed.





6 · Suggested path


    
  
  1. Now — design in JS (this page). Iterate the grammar where a change costs a page reload. Grow corpus.json as decisions land.
    2. 
  
  2. Port to Rust as rs/core/src/clx_lang.rs: lexer → parser → Vec<Binding> → the engine's existing module dispatch. The action side calls the Cmd executor that already exists.
    3. 
  
  3. Swap the lab to WASM. Expose compile(src) -> JSON through the browser adapter; this page loads it and the JS twin becomes a fallback. Run the corpus against both in CI.
    4. 
  
  4. Round-trip with the recognizer. edges(pattern) here produces exactly what gesture-parser reads; feed one into the other and assert identity. That is the reverse direction asked for earlier, without JS ever needing to inject a key.
    5. 
  
  5. Then when scoping (§3) — parser change is small, but it needs the foreground-window cache and a WinEventHook first, or it lands on the hot path.
    6. 
  
  6. Then the js escape hatch (§4) — script worker thread, one QuickJS context, clx.d.ts. Port App-OneNote as the proving case; it is 86 SendEvent + 29 clipboard calls and nothing else.
    7. 
  
  7. tree-sitter only when someone wants highlighting in an editor.

7 · Open design questions




#QuestionCurrent draft says



Q1Is a .clx file the whole config, or just bindings?Just bindings. Speeds, API keys, feature toggles stay in prefs. Keeps the language small and the file diffable.


Q2Punctuation keys: bare (- =) or named (minus equal)?Both accepted for -/= because F11/F12 use them constantly; everything else by name, since . | + are operators.


Q3What does the engine do with a pattern whose hold is a non-trigger, e.g. alt[ 1 ]?Undecided. Today the engine only dispatches while a trigger is held. Allowing arbitrary holds is a much bigger engine change than the parser suggests — flag it before anyone writes one.


Q4Sequences at top level — clx[ g ] clx[ g ] as a double-tap?Decided: no. There is no double-tap feature (why). A top-level sequence still parses but is not simulated and should be rejected by the Rust parser.


Q5Built-in names: closed set or free-form?Free-form in the parser, resolved by the engine, unknown names rejected at load time with a diagnostic — so adding a built-in never touches the grammar.


Q7Element targets: match by exact name, substring, or glob? Case-sensitive?Undecided. Exact-then-substring with a diagnostic on ambiguity is the usual compromise; needs a real UIA/AX backend to test against.


Q8Should click with no target mean "where the pointer is" or "where the gesture started"?Pointer position. Gesture-start needs the engine to snapshot the cursor on trigger-down, which is cheap — worth adding as @start rather than changing the default.


Q9Multi-monitor: are 400 300 and 50% 50% primary-display or virtual-desktop coordinates?Primary for percent, virtual for absolute px — that matches what SetCursorPos and CGWarpMouseCursorPosition actually take. Needs stating loudly in docs either way.


Q10Can a when predicate ever be user code?Decided: no. It gates suppression, so the hook must answer it synchronously — app/class/title against the cached foreground window, nothing else. Same constraint as Q11, showing up in a second place. (§3)


Q11Can a js { } handler suppress the key?Decided: no. Suppression is declared by the pattern; the script is posted to a worker and forgotten. Free to decide now, painful later. (§4)


Q12Which script runtime, and is it TypeScript?Leaning rquickjs on quickjs-ng, Boa as the no-C-toolchain fallback. TS via a shipped clx.d.ts for the editor, no typechecker in the binary; oxc_transform stripping only if annotations actually get written. (§4)


Q13Is when scoping enough to port the App-* modules, or do they need per-control focus too?Undecided. App-OneNote uses ControlGetFocus in two places, which app/class/title cannot express. Likely a control: matcher — but it costs a focus query on the hot path, so it needs measuring before it is promised.


Q6Where does the file live and when is it reloaded?Suggest ~/.config/capslockx/bindings.clx (Windows: %APPDATA%), hot-reloaded on save, with load errors shown in the tray and the previous good set kept.
