Where the language is ahead of the engine

  
The Platform trait today has mouse_move(dx, dy) — relative only — plus mouse_button and scroll_v/h. There is no cursor-position getter, no absolute move, no window rect, no screen size, and no element lookup. Even the agent's m c (click where the pointer is) is unimplemented in clx-agent.rs ("will fix with proper tracking"). So of the target forms above, only cur offsets and marks run on the engine as it stands. The rest are honest requirements, not promises — and @"element" on Windows means a UI Automation client that doesn't exist yet.






  
Pointer keys on the pattern side

  
mb1–mb5 (aliases lbtn rbtn mbtn xbtn1 xbtn2), wheelup, wheeldown parse as keys, so mb4[ h ] or clx[ wheeldown ] are writable. They are flagged with a warning: the engine hooks the keyboard only (WH_KEYBOARD_LL; a CGEventTap with the keyboard mask on macOS). Seeing mouse buttons as triggers needs a second hook, and on Windows a WH_MOUSE_LL callback shares the same UI-thread hazards this project has already been bitten by.






  
A decision made while writing this: single letters are always letters

  
The first draft had s and c as aliases for the triggers, so (s+c) was short and pleasant. It also made clx[ c ] — tile windows — silently mean CapsLock. Aliases that shadow real keys are removed; clx, space and capslock stay.





Grammar (EBNF)


file      := { line NEWLINE } ;
line      := [ binding ] [ comment ] ;
binding   := pattern "=>" action ;
pattern   := gesture { gesture } ;                     (* juxtaposition = sequence *)
gesture   := holdable ( "[" [ pattern ] [ "]" ] | "." | ε ) ;
holdable  := key | "(" key { ( "+" | "|" | "->" ) key } ")" ;
key       := IDENT | DIGIT | "-" | "=" ;               (* punctuation keys also by name: minus equal comma ... *)
action    := "{" [ command { ";" command } [ ";" ] ] "}" | command ;
command   := pointer | IDENT { arg } ;
arg       := IDENT | NUMBER | DURATION | STRING | MODKEY ;
pointer   := ( "m" | "hover" ) target [ "c" ]
           | ( "click" | "dbl" ) [ button ] [ target ] [ "x" DIGITS ]
           | "drag" target "->" target [ button ]
           | ( "md" | "mu" ) [ button ]
           | "scroll" ( "up" | "down" | "left" | "right" ) [ DIGITS | PX ] [ target ]
           | "mark" IDENT ;
target    := coord coord | ( "win" | "cur" | "screen" ) coord coord | "cur"
           | "@" IDENT | "@" STRING | "@" IDENT ":" STRING ;
coord     := [ "+" | "-" ] ( DIGITS | PCT ) ;
button    := [ MODS ] ( "l" | "r" | "m" | "x1" | "x2" ) ;
MODKEY    := ( "c-" | "s-" | "w-" | "a-" )+ IDENT ;
DURATION  := DIGITS ( "ms" | "s" ) ;




  
The one design move that makes this cheap

  
The action half is not new. clx agent --exec already parses and executes k/m/w/wf/scan (parse_line in clx-agent.rs). A .clx binding's right-hand side is a line of that language, so the engine can hand it to code that already exists. Only the pattern half is genuinely new — and it is the notation the recognizer already speaks.

The grammar above is about 14 token kinds and no left recursion. That constrains the answer more than any library's feature list does.

What actually keeps two implementations honest: a conformance corpus, not a shared grammar

  
Whatever parses .clx in the lab and whatever parses it in the engine must agree. A shared grammar file feels like the guarantee but isn't — the semantic layer (aliases, duplicate detection, edge IR) lives outside the grammar. A directory of .clx inputs with expected {bindings, edges, diagnostics} JSON that both implementations must pass is the guarantee, and it doubles as the language's spec-by-example. The JS side already proved this works: parse.test.cjs caught two real bugs a visual check had missed.

5 · Open design questions




#QuestionCurrent draft says



Q1Is a .clx file the whole config, or just bindings?Just bindings. Speeds, API keys, feature toggles stay in prefs. Keeps the language small and the file diffable.


Q2Punctuation keys: bare (- =) or named (minus equal)?Both accepted for -/= because F11/F12 use them constantly; everything else by name, since . | + are operators.


Q3What does the engine do with a pattern whose hold is a non-trigger, e.g. alt[ 1 ]?Decided 2026-09-15, in two halves. A modifier hold (alt[ 1 ]) is a global hotkey — the engine already has one hard-coded (Ctrl+Cmd+Shift+T) and modifiers are never deferred, so it is cheap. A plain-key hold (f[ j ]) is a tap-hold: f must be buffered until the engine knows whether a body follows. The parser now warns on it; the v1 loader rejects it. Why, with numbers →


Q4Sequences at top level — clx[ g ] clx[ g ] as a double-tap?Decided: no. There is no double-tap feature (why). A top-level sequence still parses but is not simulated and should be rejected by the Rust parser.


Q5Built-in names: closed set or free-form?Free-form in the parser, resolved by the engine, unknown names rejected at load time with a diagnostic — so adding a built-in never touches the grammar.


Q7Element targets: match by exact name, substring, or glob? Case-sensitive?Undecided. Exact-then-substring with a diagnostic on ambiguity is the usual compromise; needs a real UIA/AX backend to test against.


Q8Should click with no target mean "where the pointer is" or "where the gesture started"?Pointer position. Gesture-start needs the engine to snapshot the cursor on trigger-down, which is cheap — worth adding as @start rather than changing the default.


Q9Multi-monitor: are 400 300 and 50% 50% primary-display or virtual-desktop coordinates?Primary for percent, virtual for absolute px — that matches what SetCursorPos and CGWarpMouseCursorPosition actually take. Needs stating loudly in docs either way.


Q6Where does the file live and when is it reloaded?Suggest ~/.config/capslockx/bindings.clx (Windows: %APPDATA%), hot-reloaded on save, with load errors shown in the tray and the previous good set kept. Prior art agrees on "previous good set kept": keyd needs an explicit keyd reload, kanata a lrld key action, Karabiner watches its JSON — none of them apply a broken file.


Q10Per-application bindings — clx[ h ] => k left only in the terminal?Open. Karabiner's frontmost_application_if is the only prior art among the four surveyed (keyd, kanata and QMK sit below the window system and cannot know). CLX does know the foreground window, so a guard is expressible; the question is syntax — a prefix (@app "Terminal": clx[ h ] => …) or a section header. Not needed for v1; the modules have no per-app behaviour today either.


Q11Are scan, S, ? (agent-runtime verbs) valid actions?Decided 2026-09-15: no. The action side is the stable subset of the agent language — k m w wf plus the pointer verbs and built-ins. scan/S/? belong to a running agent session, not to a binding file; they fail to parse here and the corpus pins that.


Q12Is clx[ ] (empty hold body) a tap?Decided 2026-09-15: warn. It would behave as a tap, but the notation already has clx. for that, and an empty body is far more often a half-typed binding.

What the canonical form compares

  
Three lists, order-sensitive: bindings as "<line>: <normalized pattern> => { cmd; cmd }", variants as the trace form the recognizer already emits ([space h space]), and diags as "level@line: message" — level and line exact, message matched by prefix, so wording can be tightened without touching 47 cases. The Rust port needs to print exactly this; nothing else about its AST is constrained.

Two things the survey says the draft has right

  
Body keys firing on key-down. Every other tool waits — for a term, for a release, for a chord timeout — because its hold keys are letters that must still type. CLX's holds are dedicated keys whose own output is cheap to defer (a space, a caps toggle), so it can act on the first body key-down with zero added latency. That is a property of choosing CapsLock/Space, and the notation should keep it explicit rather than grow per-binding timeouts.

  
Chords from the held set, not a timer. keyd, Karabiner and QMK all put a 50 ms window on simultaneity. CLX's (capslock+space) is a set membership test, so it is order-free and never mis-times. The cost is that only keys the engine already suppresses can be chord members — which is exactly the trigger set, and exactly why plain-key chords like (j+k) are a Q3 problem, not a syntax one.





  
Two things every other tool has that .clx doesn't

  
One-shot. Tap the layer key, the next key gets the layer. It is the standard answer to "I want Space+H without holding Space while I think". Cheap in the engine (a flag consumed by the next key-down) and it has an obvious notation — but it is a new gesture kind, so it belongs in the recognizer first. Parked.

  
An escape hatch to the shell. keyd's command(), kanata's cmd, Karabiner's shell_command. The agent language has none, and .clx inherits that. Worth keeping out: a bindings file that can run arbitrary commands is a different security posture from one that can only press keys.

Why alt[ 1 ] is cheap and f[ j ] is not


Every rule above works because a trigger's own output is deferrable: the engine suppresses the key-down and decides later what, if anything, to emit for it. Modifiers are the other class of key that needs no deferral — their key-down has no visible output, the OS tracks them, and the engine already reads them from held_keys. So a top-level alt[ 1 ] is a global hotkey, structurally identical to the Ctrl+Cmd+Shift+T special case in on_key_event step 3c: match on key-down against held modifiers, suppress, act. The only new work is a table lookup instead of an if.


A plain key is different. For f[ j ] to work, f-down must be swallowed and held back until either j arrives (hold: run the action, never type f) or f is released (tap: type f now, late). That is home-row-mod territory, and the survey shows what it costs everyone who does it:


    
  
  • An input buffer with replay. With HOLD_ON_OTHER_KEY_PRESS semantics — the engine's current rule — typing fj fast (f↓ j↓ f↑ j↑, QMK's "rolling" case) becomes the hold action, never fj. Every tool that supports letter holds therefore offers PERMISSIVE_HOLD / tap-hold-release, which means j-down must also be held back until j-up or a timeout decides. The engine has no such queue today; it decides everything on the event it is handling.
    • 
  
  • A tapping term per key, and a timer to enforce it. The one timer the engine has is the 200 ms Space thread, and it is the thread the double-tap page catalogued as a bug class: when the hook died it became an unbounded SendInput loop. Generalizing it to N keys multiplies that surface.
    • 
  
  • Configuration surface. kanata exposes two timeouts and eight variants per key; QMK five global modes plus per-key overrides. The moment .clx allows letter holds it needs at least a term and a policy, and the one-page grammar stops being one page.
    • 




  
Decision for v1 (2026-09-15)

  
The holder of a top-level hold must be a trigger (space, capslock, insert, scrolllock, the clx alias, or a commutative group of them) or a modifier (alt, ctrl, shift, win, or a group of modifiers). Inside a body, modifiers may nest freely (clx[ shift[ 3 ] ]). Plain-key holds parse — the notation is deliberately more general than the engine — but the parser warns and the loader rejects them with the same message, so a file that loads is a file whose every binding is zero-latency. The corpus pins this (hold on a plain key is a tap-hold).

  
If letter holds are ever wanted, the shape is known: it is the tap-hold-release policy with a per-binding term, and it needs the event queue first. That is an engine project, and it should be started from the recognizer side (the gesture parser would need to emit deferred events) rather than from the grammar.
