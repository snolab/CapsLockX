Script store

Shipping a compiled executable per feature is the wrong shape for a hotkey tool. Scripts are the right one — and most of what that needs is already compiled into clx. This is the design, the order to build it in, and the one part that deserves genuine caution.

Why not another exe

clx-genpw exists as a compiled binary. It is about twenty lines of real logic — pick characters from an alphabet, print one line — wrapped in a Rust crate, a build target, and a deployment step. Doing that again for the next small idea is how a tool accumulates a distribution problem instead of features.

ConcernCompiled pluginScript
Platforms One build per target; cross-compiling for macOS from Windows is its own project One file, everywhere
Antivirus An unsigned executable that injects keystrokes. Defender already quarantined clx for hook + injection + spawning processes; a store that downloads and runs binaries is the worst possible shape for that heuristic Nothing is spawned; no new image on disk to flag
Review before trusting You cannot read a binary You can read the file
Iteration Edit, build, sign, deploy, restart clx Edit, press the key
Process cost A spawn per invocation In-process

The plugin contract still holds

A plugin is anything that emits effects. A script is not a different contract, only a different way of running one — the effects, and the fact that clx knows nothing about what they are for, are unchanged. clx plugin <program> stays useful for anything that genuinely needs to be a program (otoji, a model server); scripts are for the long tail that does not.

What already exists

This is less new machinery than it sounds. Three pieces are already in the tree:

  • A JS engine, already compiled in. rquickjs for native builds, boa for WASM (rs/core/Cargo.toml:89), with a working js_eval in rs/core/src/agent.rs:261. Nothing needs to be added to run a script.
  • The effect language. rs/core/src/effects.rs — the output format a script would emit, already parsed, already performed, already tested.
  • The js { … } escape hatch, already designed in clx-lang and described there as opaque to the .clx around it.

What is actually missing

Not the store. Two things underneath it, and the first is the one that blocks everything:

There is no way to bind a key to anything user-defined

ClxConfig (rs/core/src/state.rs) is a flat struct of typed settings — cursor_speed, use_space, API keys. There is no map from a gesture to a command, and no extension point. That is why clx-genpw can currently only be run from a shell, which is not a feature anybody will use.

A store of scripts that cannot be bound to a key is a catalogue.

The second is the API surface. A QuickJS context has no crypto, no clipboard, no window access, no filesystem. A script can compute and emit effects and nothing else — which is a good default, and means every capability is a deliberate decision rather than an inherited one.

The binding format

Bindings belong in a file the user edits, not in the typed config struct — the whole point is that clx should not need to know the set of possible actions in advance. A small table keyed by gesture: 

# scripts/bindings.clx  — gesture on the left, what runs on the right

space+p    script  genpw.js dpw       # generate a password, type it
space+;    script  genpw.js qpw
space+d    script  isodate.js         # 2026-09-27
space+m    plugin  ay pi              # an existing program, unchanged

Two verbs, because the difference is real: script runs in-process in the JS context with the host API; plugin spawns a program and reads its stdout, exactly as today. Everything else — which gestures are legal, how a chord is written — is clx-lang's problem, already designed.

A script is a function that returns effects

The simplest contract that works, and it keeps the script honest: it cannot do anything, only describe what should happen. 

// scripts/genpw.js
export default function (args) {
  const alphabet = "123456789abcdefghijkmnopqrstuvwxyz";   // no 0 O I l
  const upper    = "123456789ABCDEFGHJKLMNPQRSTUVWXYZ";
  const pick = (set, n) =>
    Array.from(clx.random(n), b => set[b % set.length]).join("");

  const pw = pick(upper, 1) + pick(alphabet, 6) + "_" + pick(alphabet, 7);
  return [{ type: pw }];        // one effect: type this
}

clx.random is not a convenience

It is the reason this script can exist at all. Math.random() is not a CSPRNG, and the AHK original's clock-seeded Mersenne Twister is exactly the defect the Rust port was written to fix. If the host does not expose the OS CSPRNG, a scripted generator is a step backwards from the binary — so this API is a precondition for retiring clx-genpw, not a nice-to-have.

The host API is the security boundary

Every function the host exposes is a capability granted to every script. The interesting question is not what to add but what to refuse, and the answer should be written down before the first script asks.

CapabilityVerdictReasoning
clx.random(n) yes OS CSPRNG. Without it, scripted generators are weaker than the thing they replace.
Return effects yes The whole contract. Nothing else needs to be able to act.
clx.now(), formatting yes Half the AHK hotstrings are date stamps. Inert.
clx.clipboard read: careful Reading the clipboard reads whatever the user last copied, which is routinely a password or a token. Writing is far safer than reading.
Network no Read-the-clipboard plus send-it-somewhere is the entire exfiltration path in two capabilities. If a script needs the network it can be a plugin, where the user is granting a program, not a snippet.
Filesystem no Same argument. A scratch key/value store would cover the real uses.
Reading keystrokes no A script that can observe typing inside a process that already holds a global keyboard hook is a keylogger with extra steps.

Build order

1
Key → script binding

The blocker. Unblocks clx-genpw immediately and is the prerequisite for everything below. Nothing else is worth starting first.

2
A scripts/ directory in this repo

Genpw as JS, the date stamps, the demo. A bundled collection: most of the value of a store, none of its trust problem, and it is where the API surface gets discovered honestly rather than guessed.

3
The host API, deliberately

Including the refusals above, written down with reasons.

4
Metadata, only when discovery hurts

A name, a description, which platforms, which gesture it wants. Premature before there are enough scripts to need finding.

5
Third-party distribution — last, or never

See below. This is the only part where being slow is the correct engineering decision.

Third-party distribution, and why it comes last

The closest precedent is not a package manager

It is AHK script sharing, which has been a reliable malware vector for years — for exactly this reason: a keyboard tool with a global hook running a snippet someone found online. A clx script cannot read keystrokes or reach the network under the surface above, and that is deliberate, but "installed scripts type into your session" is close enough to a keylogger that the distribution story deserves more care than the runtime does.

Practical consequences, if it ever gets built: scripts arrive as readable text and are shown to the user before first run; capabilities are declared and granted rather than assumed; and a script from a store is not the same trust tier as one the user wrote. None of that is hard, but all of it is pointless before stages 1–3 exist.

Open questions

What gesture invokes a script that needs a parameter?decide first

Under a held trigger nearly every letter is taken — HJKL, YUIO, G, T, N, P, WASD, V, B, M, Z, X, C, 1–9. The generator alone wants nine profiles. One key that cycles, a two-key sequence, punctuation, or arguments in the binding table as sketched above?

JS, or the declarative .clx first?

clx-lang proposes both, with JS as the escape hatch. Most of the AHK hotstrings this replaces are one line and need no logic — a date format, a fixed string. Those may not want a JS engine at all, which would make the declarative layer the more valuable half to build first.

Does clx-genpw survive as a binary?

Its tests are a usable spec for the nine profiles and for escaping a password into the effect language. Once clx.random exists the binary is redundant — but until then it is the only working version.
