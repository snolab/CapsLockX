Plugins

CLX is a hotkey engine. It should not know what speech recognition is, or translation, or note-taking — only how to notice a gesture and hand it to whoever asked for it. This is what falls out of taking that seriously.

1 · otoji is already a plugin — informally

Nothing here starts from zero. Speech input already runs as a separate program that CLX finds at runtime and talks to over a structured protocol:

What a plugin needsotoji today
separate processits own binary, its own repo (lib/otoji)
found at runtimewhich otoji, PATH, or beside the CLX binary
own lifecycleCLX spawns it detached; it outlives individual gestures
own permissionsthe microphone grant belongs to otoji, not CLX — CLX must never request it
own configurationits own config file and settings panel
structured protocolJSON-line AsrEvents on stdout

The one thing missing: CLX knows its name

rs/core/src/modules/voice_otoji.rs is 1,195 lines that hard-code otoji's command-line flags, its process name, its companion tray binary and its config paths. So the question is not whether to build a plugin system — it is how to turn an arrangement that already exists into a contract.

2 · A plugin is something a binding can call

The obvious design is a capability taxonomy — plugins declare provides: stt, CLX binds voice keys to whatever provides it. That is wrong, and it is wrong in an instructive way: it still makes CLX learn a vocabulary of domains. Add text-to-speech and you add a category. Add translation and you add another. CLX accumulates knowledge of a problem space it has no business understanding.

Drop the taxonomy entirely. A plugin registers a name, and a .clx binding calls it:

clx[ v ] => otoji listen        # CLX has no idea what "listen" means
clx[ b ] => brainstorm
clx[ m ] => agent

The .clx draft already left the door open for exactly this. Its action grammar says of built-ins:

"Anything that isn't an agent verb is a built-in name plus args; resolved by the engine, not the parser."

Becoming a plugin host means changing the engine knows these names into whoever registered this name. CLX reduces to: notice a gesture, look up who claimed the name, hand it over. Domain knowledge: none.

3 · Effects, not domains — the one thing CLX must know

There is a limit to how ignorant CLX can be, and it is worth stating precisely, because it is easy to mistake for a hole in the idea.

CLX is the process holding the keyboard hook and the input-injection APIs. A plugin should not have to reimplement key injection, overlay rendering, or accessibility-tree targeting just to put a word on screen. So CLX has to understand what to do — while still not understanding why.

Plugins emit effects; CLX performs them

"Type this text" is an effect. "This is speech recognition" is a domain. CLX needs the first and must stay innocent of the second.

CLX already has that vocabulary. The agent language is a list of effects and nothing else:

k "the recognised words"    # CLX types it, and has no idea where it came from
k c-c                       # a chord
m 400 300 c                 # move and click
w 200ms                     # wait
wf "Save" 3s                # wait for an element

So the contract can be stated in one line:

A plugin is a process that speaks the CLX effect language on stdout

No SDK, no linking, no ABI. Any language that can write to stdout can be a plugin, and CLX already has the executor for it.

Honest gap: that executor currently lives only in the macOS agent binary (clx-agent.rs, --exec), not in rs/core, so Windows has no way to run it. Lifting it into core is the first piece of work, and it is worth doing regardless — it is the same executor the .clx action half needs.

4 · Four questions to settle before writing code

These are chosen because getting 2 and 3 wrong is expensive to undo later.

Q1 — Streaming and revision needs a decision

otoji emits a fast draft and then a corrected version; today voice.rs replaces the text in place. A pure "type this" effect cannot express that — the second version would be typed on top of the first. Either the effect language grows a notion of "replace what I last emitted", or plugins own their own correction and only emit final text. The first is more useful and more complex.

Q2 — Does the channel go both ways? needs a decision

Push-to-talk means the plugin has to learn that the key came up. That makes stdin an event channel, not just stdout an effect channel, and turns a plugin from a producer into a participant in the gesture. Skipping it limits plugins to fire-and-forget; adding it means defining what CLX tells them and when.

Q3 — Lifecycle needs a decision

otoji is a resident daemon; it holds the microphone open and outlives any single gesture. Other plugins will be one-shot. Supporting both means defining who starts what and when; supporting only one means picking which kind of plugin is second-class.

Q4 — Failure

A plugin that dies mid-gesture must not leave CLX latched. We have just spent a night on exactly this failure mode in the physics models, so the lesson is fresh: the thing that stops must not depend on the thing that broke.

5 · How we will know the design was right

There is a number to aim at, and it is unambiguous.

Lines in CLX that know otoji exists: 1,195 → 0

voice_otoji.rs hard-codes otoji's flags, its process name, its companion tray binary and its config paths. If the design is right, every one of those lines becomes otoji's own problem, and CLX keeps a generic plugin runner that would host a second plugin without being edited.

The weaker but earlier signal: adding a hypothetical second plugin should require no change to CLX at all — only a .clx binding and a program that writes effects to stdout.

Design only. Nothing here is implemented. The first piece of work it implies — lifting the effect executor out of the macOS agent binary into rs/core — is worth doing on its own merits, since the .clx action half needs the same executor.
